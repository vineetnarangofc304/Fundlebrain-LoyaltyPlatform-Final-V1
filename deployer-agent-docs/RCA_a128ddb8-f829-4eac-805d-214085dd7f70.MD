# RCA — Store KPI report hides old migrated data (KAZO / FundleBrain)

**Scope:** READ-ONLY production diagnosis. No data or config modified.
**DB:** `kazo-data-platform-kazo_fundle_db`  ·  **Run:** a128ddb8-f829-4eac-805d-214085dd7f70
**Endpoint under review:** `GET /api/kpi-reports/store-kpi`
**Tooling note:** performed with `find/count/distinct` only (no `aggregate` available), so revenue `$sum` and server-side `$dateFromString/$year` conversions could not be executed; date-bucketing was done via `^YYYY` string prefixes, which is valid here because every `bill_date` is a `YYYY-MM-DD…` string (see §2).

## BOTTOM LINE (answer to Q5)
Selecting an OLD date range **does** return the old bills at the DB level — the report's own filter for FY2023 matches **145,566** documents. They vanish **not** because of `bill_date`, but because **93% of transactions (100% of everything before 2026) have `store_id = null`**, and the Store-KPI report groups by `store_id`. The migrated bills collapse into a single null bucket / are dropped by the store grouping-join, so they never surface as their real stores.

**Root cause = missing `store_id` (and `store_code`) mapping on migrated `historic_upload` data. NOT a `bill_date` type/format/timezone problem.** The date-string filter is a red herring — it works.

## 2. Storage type & format of `bill_date`
- `$type:"string"` → **801,616 (100%)**. `$type:"date"` = 0, `null` = 0, missing = 0.
- Regex `^\d{4}-\d{2}-\d{2}` → **801,616 (100%)**. `^dd/mm/yyyy` = 0, `^dd-mm-yyyy` = 0.
- **Conclusion: `bill_date` is uniformly an ISO-8601 string. Lexical `$gte/$lte` comparison is correct for every document.** The type/format theory does not hold.
- Sample raw values:
  - OLD (`source:historic_upload`): `"2023-12-31T22:17:00+00:00"`, `"2021-04-01T00:00:00+00:00"` — UTC offset `+00:00`
  - RECENT (`source:pos_ewards`): `"2026-09-21T17:53:05+05:30"` — IST offset `+05:30`
- **Secondary note (timezone edge, NOT the root cause):** old data is stamped `+00:00`, live data `+05:30`. The string prefix still sorts by stored wall-clock, but because the two sources use different reference zones, a handful of near-midnight bills at FY boundaries (Apr 1 / Mar 31) can land on the adjacent day. Minor boundary leakage only; does not explain the missing bulk.

## 3. Reproduction of the report's FY2023 OLD-range filter
- Report filter `{"bill_date":{"$gte":"2023-04-01","$lte":"2024-03-31T23:59:59Z"}}` → **145,566 documents match.**
- Of those 145,566: `store_id = null` → **145,566 (100%)**;  `store_id` is a real string → **0**.
- ➡️ The date filter DOES see the old data (145,566 rows). Every one of them has a null store_id, so the group-by-store_id step is where they disappear. (Revenue `$sum` not computable without `aggregate`; per-doc revenue fields present: `bill_amount`, `net_amount`, `gross_amount`, `amount_paid`.)

## 4. store_id / store_code mapping
- `store_id = null`: **746,450 (93.1%)**
- `store_id` = string (mapped): **55,167 (6.9%)**;  `store_id = ""`: 0
- distinct `store_id`: **65** (64 real ids + null)
- `store_code = null`: **753,326 (94.0%)**;  fully mapped (store_id AND store_code both strings): **48,291**
- `store_name = null`: only **56** (store_name is almost always populated, even on null-store_id bills — 76 distinct names among null-store_id docs)
- By source: `historic_upload` = **751,102 (93.7%)**  ·  `pos_ewards` = **50,515 (6.3%)**
- By year, mapped vs null:
  - 2025: total 212,293 → mapped **0**, null 212,293
  - 2026: total 124,166 → mapped **50,270**, null 73,896
  - ➡️ Mapped store_ids exist **only from 2026** (the live-POS `pos_ewards` era). All FY2021–FY2025 migrated data is store_id-null.
- "ECom Application" (the one store the report surfaces): **53,888 bills, ALL store_id null** (2026 portion 5,880).

## Why the report shows only a small recent slice
The Store-KPI report groups by `store_id`. Only the ~50k live-POS (2026) bills carry a real `store_id`; the 746k migrated bills (all of FY2021–FY2025 + all `historic_upload`) have `store_id = null`, so they either collapse into one null group or are excluded by the store join/lookup — they never appear as their real stores. The visible "small recent slice" is the mapped POS data; the migrated history is present in the DB but invisible to a `store_id`-keyed grouping.

## Recommended fix (for app/source team — NOT applied here)
1. **Backfill `store_id`/`store_code` on `historic_upload` transactions** by mapping the already-present `store_name` → `stores` collection (157 store docs exist). This restores the migrated bills to their stores in every store-keyed report. **(Preferred, root-cause fix.)**
2. And/or make the report resilient: group by `store_name` (or `COALESCE(store_id, store_name)`) as a fallback when `store_id` is null, use a LEFT join (not inner) to `stores`, and surface an explicit "Unmapped" bucket so null-store data is never silently hidden.
3. Do **not** change `bill_date` handling — it is correct.
