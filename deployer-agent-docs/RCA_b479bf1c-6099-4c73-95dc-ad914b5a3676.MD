# RCA — SMS Delivery Reports (DLR) stuck at "Pending" (delivery_status="submitted")

**App:** KAZO loyalty / FundleBrain CRM (`kazo-loyalty-hub`)
**Run:** b479bf1c-6099-4c73-95dc-ad914b5a3676 (active, success) · tier_3 · fastapi_react_mongo_shadcn · cloudflare frontend
**Prod URL:** https://kazo-loyalty-hub.emergent.host · custom domain https://kazoloyalty.fundlebrain.ai (verified)
**Prod DB:** kazo-data-platform-kazo_fundle_db
**Scope:** Diagnosis only (no production data intentionally changed — see caveat at end).

## VERDICT
**Root cause = (B): Karix is NOT calling the DLR webhook.** The callback is not actually active/registered on the Karix side, or is pointed at the wrong URL/domain. The Emergent side — endpoint, public routing, and the `_ingest_dlr` matching logic — is fully correct and working. Because Karix never pushes a DLR and no pull endpoint is configured, delivery status can never advance past "submitted".

## EVIDENCE

### A) Reachability / routing — PASS (endpoint works end-to-end)
Direct hit to the production URL:
`GET https://kazo-loyalty-hub.emergent.host/api/communications/dlr/karix?mid=TEST&status=DELIVRD&dest=919999999999`
→ **HTTP 200**, `application/json`, body:
`{"ok":true,"matched":1,"status":"delivered","mid":"TEST","auto_blacklisted":false}`
The endpoint is public (no auth), routed to the backend pod (not a 404/401/502/ingress error), and the matching logic fired correctly — it matched a submitted row by the last-10-digit mobile fallback and set it delivered. So routing AND matching are proven functional in production.

### B) Is Karix actually calling it — NO (this is the cause)
Pod access logs (Loki, last 24h — the max window the tool allows; 48h not retained):
- Filter `dlr/karix` over 24h → **exactly 1 line**, and it is my own test probe:
  `INFO: 34.49.222.149:0 - "GET /api/communications/dlr/karix?mid=TEST&status=DELIVRD&dest=919999999999 HTTP/1.1" 200 OK`
- Filter `dlr|karix|communications` over 24h → only outbound `GET /api/communications/bulk-jobs…` UI calls. **Zero inbound DLR requests from Karix (GET or POST).**

### C) Being called but not matching — NOT the cause (no DLR ever arrived)
`message_log` collection (19,432 total rows):
- `delivery_status` distinct values = **["delivered","submitted"]** (no "failed" ever recorded).
- Rows with `delivery_status="submitted"` = **19,432** — i.e. effectively everything is pending.
- Rows with `dlr != null` = **1**; rows with `delivery_status="delivered"` = **1**. **That single row is my synthetic TEST probe** (confirmed: `{dest:"919999999999", mid:"TEST", status:"DELIVRD"}`, mobile 919999999999).
  → Before the probe, **ZERO rows had ever received a DLR** and **ZERO were ever delivered**.
- Rows `submitted` AND `dlr != null` = **0** → there is NO "a DLR arrived but failed to match" case. If Karix were calling and failing to match, we would see populated `dlr` with status still "submitted"; we see none.
- `provider_mid` IS being captured at submit time: `channel="sms"` with `provider_mid != null` = **19,400** of ~19,432. Sample values are 19-digit numeric Karix message IDs (e.g. `1383251713046780200`, `1283251713184883500`). So exact `provider_mid == mid` matching would also work the moment real DLRs arrive.
  - Minor/secondary note: the ~32 rows without `provider_mid` are concentrated in the most-recent sends (the 10 newest submitted rows all show `provider_mid=null`). This does NOT block anything today (no DLRs arrive at all), and even for those rows the last-10-digit mobile fallback would match. Worth a glance later, but it is not the cause.

### D) provider_config — pull fallback is unavailable
Single provider_config doc. Presence only (no secret values read):
- `sms_api_key` — **present**
- `sms_sender_id` — **present** ("KAZOFN")
- `dlr_pull_endpoint` — **ABSENT**
→ The secondary PULL path (`POST /api/communications/dlr/pull`) cannot run because `dlr_pull_endpoint` is not configured. DLRs therefore depend entirely on the Karix webhook, which (per B) is not firing.

## WHY STATUS STAYS "Pending"
SMS submit correctly stores `message_log` rows (`delivery_status="submitted"`, `provider_mid` populated), but no DLR callback ever reaches the backend (0 inbound hits; 0 stored DLRs across 19,432 rows). With no push from Karix and no pull endpoint configured, nothing ever flips "submitted" → delivered/failed. The webhook handler and matcher are proven working by the direct probe.

1. In the Karix (InstaAlerts) account, confirm the **DLR / delivery callback URL is registered AND active**, pointing to the production URL:
   `https://kazo-loyalty-hub.emergent.host/api/communications/dlr/karix`
   (or the custom domain `https://kazoloyalty.fundlebrain.ai/api/communications/dlr/karix`).
   Verify it is NOT pointed at a preview/`*.emergentagent.com` domain, and that callbacks are enabled for the sending account/sender ID "KAZOFN".
2. Ask Karix to trigger/confirm a test DLR, or send one live SMS, then re-check pod logs for an inbound `POST/GET /api/communications/dlr/karix` and confirm the corresponding `message_log` row flips to delivered.
3. (Optional fallback) If Karix exposes a DLR pull API, set `dlr_pull_endpoint` in `provider_config` so `/api/communications/dlr/pull` can be used; currently it is absent.
4. (Minor, non-blocking) Investigate why the most recent SMS sends store `provider_mid=null` (Karix accept-body parsing for ackid / "Request ID="). Not the current cause; mobile-tail fallback still matches, but exact-mid matching is more reliable.
